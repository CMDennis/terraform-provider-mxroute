# API contract decisions

Status: Phase 0 design record with Phase 7 read-only evidence, based on `api/snapshots/openapi-2026-10-19.yaml` (OpenAPI 3.0.3, API 1.0.0). All fourteen ordinary-account reads passed authorized live checks. A later explicit request also authorized isolated creation and quota/limit/password updates of one new mailbox, plus its Terraform import/no-change plan. Existing objects, deletion and reseller/impersonation were not tested through live mutations. The examples in `testdata/contracts/scenarios.json` are synthetic fixtures. A response shape explicitly marked hypothetical is a test input for defensive behavior, not evidence of MXroute runtime behavior.

The snapshot declares 43 HTTP operations across 26 paths. It has no `operationId`s, pagination parameters, or bulk/import paths. The `Bulk/import` rate-limit row is not an operation contract and does not justify inventing an endpoint. `/quota` and `/quota/email` document unwrapped JSON objects; Phase 7 observed standard success/data envelopes on both, and the client now accepts either complete shape; most other documented JSON successes use `{success,data}`. Several 201, 200 mutation, and 204 responses declare no body schema or content. Treat a body as usable only where the operation documents one; do not require a returned object for a successful sparse mutation.

## Contract issue register

| --- | --- | --- | --- |
| C01 | `GET/PATCH /domains/{domain}/spam/settings`; sender list methods | Sender entries have effective-account ownership with an owned access domain. Phase 5 conservatively gives spam scoring one account owner with ID `spam-settings`, independent of access domain, because saves affect shared scoring. Never expose independent per-domain resource copies. Exact selected-domain versus shared-value propagation and production readback remain Phase 7 validation questions; the preview is not a stabilized live contract. | The pinned tag establishes account-wide sender lists. Additional public evidence, read October 19, 2026: [MXroute Spam Filters and Sender Lists](https://docs.mxroute.com/docs/panel/spam-filters.html) describes score saving as affecting shared scoring as well as the selected domain. Account ownership is a conservative inference from those shared effects, not proof that every domain GET returns an identical score. Mocks exercise one shared score; production propagation remains live-unverified. |
| C02 | `POST /domains/{domain}/forwarders`; `DELETE /domains/{domain}/forwarders/{alias}` | Treat alias and destination changes as replacement. Do not promise in-place edits or create-before-destroy for an alias that may be unique. After delete/create failure, report the partial outcome; do not retry blindly. | The snapshot documents create and delete only. There is no update method or request contract. This supports replacement as the only documented lifecycle; whether the API has undocumented mutation behavior is not assumed. |
| C03 | `GET /verification-key`; `POST /domains`; pointer list/create/delete; `GET/DELETE /domains/{domain}`; email-account operations | Require the documented TXT verification record before attempting domain creation. Call only the documented domain delete operation, never cascade client-side through mailboxes/pointers. Block live domain deletion coverage until cascades and recoverability are understood. Do not expose any assumed system-mailbox identity as a normal managed mailbox. | Verification-key description gives the sequence and record value `domain-verified`, followed by DNS propagation and `POST /domains`. A configured value that readback does not confirm after successful writes fails the apply and records the reported value. The contact email has no update route; changing it is an explicit replacement, while remote changes are reported without replacement. Never infer that a package change preserves or clears overrides. The snapshot does not state how assigning or updating a package affects existing overrides. Package POST defaults are documented, but its 201 response has no body schema. **Blocking questions:** Does package reassignment apply/reset package quota over a user's explicit quota override? Does package update affect current users? Do GET and package-change response values consistently expose effective quota and unlimited status? |
| C05 | `GET/PATCH /domains/{domain}/catch-all`; `GET/PATCH /domains/{domain}/spam/settings` | Treat each as a non-deletable singleton: resource destroy relinquishes Terraform management and preserves the remote value. | C06 | All operations; especially list GETs and documented missing/error responses | A successful, valid complete list may establish absence. ## Response handling and absence rules

1. Decode only responses whose status is documented as success for that operation. A successful 204 has no bytes (`body: null` in fixtures). Do not pass it to a JSON decoder.
2. For an operation with a documented success schema, require valid JSON and the structure needed to read the object safely. Most response properties are not marked `required` in OpenAPI: requiring `success:true`, a correctly typed `data`, and the identity/state fields needed by a lifecycle is a defensive provider contract, not a stronger claim about the published schema. Reject incomplete reads and preserve state rather than converting absent fields to zero. Envelope operations must reject `success:false`. For quota endpoints, accept the published top-level object or the Phase 7 observed standard envelope. A present success marker must validate as a complete envelope and cannot fall back to raw decoding.
3. For sparse success responses with no documented content (notably most 201 creates, update 200s, and all 204s), accept the documented status with an empty body. If a non-empty body is supplied, inspect it for the globally documented `{success:false,error}` failure envelope even on 2xx; that is an operation failure, not success. For other non-empty undocumented content, preserve the successful status and use a documented GET for readback rather than trusting an undocumented shape.
4. Treat the standard error envelope as the documented format, but fixtures for statuses whose operation only gives a prose description are illustrative variants, not verified payload guarantees. Preserve HTTP status and a safe diagnostic even if error JSON is malformed or absent.
5. Only a valid, successful complete list can establish absence by omission. For singleton or detail reads, a 404 establishes absence only if that route documents that meaning; otherwise preserve state until a successful complete list or another documented read corroborates absence. 401/403/429/5xx, malformed success bodies, and account-context errors always preserve state.

## Six Phase 0 questions: resolved scope and blockers

The decisions above resolve safe implementation direction without presenting missing runtime facts as settled contracts:

- Spam sender lists are explicitly shared at effective-account scope. Phase 5 resolves conservative score ownership from additional public evidence of shared scoring effects (C01): one account owner, independent access context. Exact cross-domain values and live readback remain unverified and block a stabilized production-compatibility claim, not the credential-free preview implementation.
- Forwarder edits are replacement (C02) because there is no update operation.
- Domain verification ordering is explicit; pointer prerequisites, domain deletion cascades, and system-mailbox identity/restrictions are not. **Blocking questions:** What pointer prerequisites apply? What does domain deletion cascade to and can deletion be recovered? Which system mailbox is reserved and what operations are allowed? C03 blocks live destructive-domain verification and any inferred mailbox lifecycle rule.
- Package defaults and returned quota fields are represented with their documented units/nullability. **Blocking questions:** Does package assignment/update preserve or override per-user quota? Which user/package readback fields reliably report the effective limit and unlimited state? C04 blocks stabilization of combined package/quota behavior.
- Catch-all and spam-score singleton destroy relinquishes management and keeps remote settings, per C05.
- No bulk/import HTTP path is documented. Terraform state import is a provider feature and does not imply an API import endpoint. Keep the coverage baseline at the 43 declared method/path operations.

## Future live prerequisites and scope

No live testing is authorized or performed in Phase 0. All current fixtures and later Phase 0–6 tests must use an explicit local mock endpoint and dummy credentials, with no production fallback.

| Capability/scenario | Prerequisite | Phase 7 live position |
| --- | --- | --- |
| Read ordinary-account domains, DNS, quota, mailbox/forwarder inventories, catch-all, spam settings/lists | Ordinary account and locally supplied credential; read-only approval and baseline inventory | Candidate for a scoped read-only check after approval. Results verify runtime only for that account. |
| Create/delete domain, pointer, mailbox, forwarder, spam entry, catch-all change | Isolated owned test domain, DNS control/verification, explicit identity manifest, approved exact writes and any cleanup | Avoid if it can affect mail, existing resources, or shared settings. Domain deletion/cascades remain blocked pending a safe sandbox/verified recovery. |
| Verify pointer setup and deletion prerequisites | Owned disposable source and target domains with DNS control | Live-unverified until isolated domains exist and effects/cleanup are approved. |
| Verify shared spam scope and entry ownership | At least two owned domains on one disposable ordinary account; baseline of lists and settings | Read-only comparison may verify sharing. Writes can affect all domains; avoid live mutation unless explicitly isolated and approved. |
| Verify spam high-score scope and singleton relinquish behavior | Disposable ordinary account or safe dedicated sandbox; baseline and recovery path | Live-unverified; never test by changing account-wide production filtering. |
| Verify reseller CRUD, package assignment effects, and `reseller|user` impersonation | Reseller privileges, at least one reseller-owned disposable ordinary user, disposable package, separate identities | Unavailable unless reseller access and a test-owned account are provided. Never create/suspend/delete an unapproved real user. **Out of scope by user decision (October 19, 2026): reseller surfaces stay mock-only and live-unverified.** |
| Verify package quota defaults/overrides, zero vs unlimited, system mailbox treatment | Reseller test account with disposable user/package and known mailbox inventory | Live-unverified until package/user ownership and cleanup are isolated. **Out of scope by user decision (October 19, 2026): reseller surfaces stay mock-only and live-unverified.** |
| Exercise 401/403/404/409/422/429/500/503 errors and success-false/malformed variants | Mock is sufficient for client contract. Live verification would need a sandbox and controlled invalid/limited scenarios. | Keep synthetic. Do not intentionally invalidate the sole real credential or trigger account lock/rate limits. |
| Test deletion/cascades or automatic teardown | Disposable sandbox whose objects and dependencies are exclusively test-owned | Never run against existing account objects. A destroy/replace of existing identity remains prohibited regardless of resource name. |

Before Phase 7 live testing, prepare the exact operation list, affected identities, expected side effects, and cleanup allowlist; capture baseline state; review each mutation and cleanup; and stop on any unexpected or ambiguous result. Possession of credentials is not authorization. No reseller account, disposable sandbox, test domains, or DNS delegation is presumed available.
